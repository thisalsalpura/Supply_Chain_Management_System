# Supply Chain Management System — Database Schema

## Overview

The Supply Chain Management System uses PostgreSQL as its backing store, accessed through plain JPA against an `EntityManager` (no Spring Data JPA, no native Hibernate `Session` API). The persistence unit is `supply_chainPU`, defined in `persistence.xml`, with `hibernate.hbm2ddl.auto` set to `update`. The schema below is therefore generated and kept in sync automatically on every deployment; this document is a reference, and a supplement for the indexes Hibernate does not create on its own.

## Entity Relationship Summary

Six entities make up the schema:

- A **`Vendor`** places many **`Order`**s (one-to-many, unidirectional from `Order` → `Vendor` via `@ManyToOne`).
- An **`Order`** owns many **`OrderItem`** rows through a one-to-many relationship with `cascade = CascadeType.ALL` and `orphanRemoval = true`, so deleting an order removes its line items automatically and a line item cannot exist without its parent order.
- Each **`OrderItem`** holds an eager many-to-one reference to the **`InventoryItem`** it represents (eager, unlike the lazy `Order`/`Vendor` references, because an order line is not useful to the caller without knowing which SKU it refers to).
- **`User`** holds its role set in a separate collection table (`user_roles`) via `@ElementCollection`, fetched eagerly since roles are needed on every authenticated request.
- **`AuditLogEntry`** and **`RefreshToken`** are standalone entities with no relationships to the others — audit rows and refresh tokens are written independently of the domain aggregate they describe.

### audit_log_entries

| Column      | Type         | Constraints                               |
| ----------- | ------------ | ----------------------------------------- |
| `_id`       | UUID         | Primary key, generated by the application |

| `reason`    | varchar(500) | Not null                                  |
| `timestamp` | timestamp    | Not null, set on insert via `@PrePersist` |

Written by `AuditLogBean.logFailedOperation()` under `TransactionAttributeType.REQUIRES_NEW`, so a row here commits independently even when the operation it describes rolls back (see Deployment Guide / design notes for why).

### refresh_tokens

| Column       | Type         | Constraints                               |
| ------------ | ------------ | ----------------------------------------- |
| `_id`        | UUID         | Primary key, generated by the application |
| `token`      | varchar(512) | Not null, unique, indexed                 |
| `username`   | varchar(150) | Not null, indexed                         |
| `created_at` | timestamp    | Not null, set on insert via `@PrePersist` |
| `expires_at` | timestamp    | Not null                                  |

Indexes on `token` and `username` are declared directly on the entity (`@Index`), so Hibernate creates both automatically — this table is the one exception to the "indexes must be added manually" note below.

## Schema Design Decisions

**UUID primary keys throughout.** All entities use `GenerationType.UUID` rather than a sequence or identity column. This avoids sequential-ID enumeration (an attacker cannot infer `/api/vendor/2` exists from having seen `/api/vendor/1`) and keeps identifiers safe to expose directly in DTOs, at the cost of a larger index footprint than auto-increment integers.

**Status fields stored as strings, not ordinals.** `@Enumerated(EnumType.STRING)` is used on `Order.orderStatus`, `Vendor.vendorStatus`, and `InventoryItem.stockStatus`, so stored values are human-readable directly in the database and a future reordering of the enum constants in code cannot silently corrupt existing rows the way `EnumType.ORDINAL` would.

**Cascade and orphan removal from `Order` to `OrderItem`.** An order line has no meaningful existence outside its parent order, so cascading persist/merge/remove from `Order` down to its `OrderItem` collection enforces that invariant at the JPA layer instead of relying on application code to clean up line items manually.

**`InventoryItem` on `OrderItem` is eager, `Vendor`/`Order` references elsewhere are lazy.** An `OrderItem` is not useful to a caller without knowing which SKU it represents, so that association is `FetchType.EAGER`; every other association (`Order.vendor`, `OrderItem.order`) stays `FetchType.LAZY` to avoid pulling in full parent aggregates on every read.

**Computed `stock_status` persisted rather than derived at query time.** `InventoryItem.computeStockStatus()` runs in `@PrePersist`/`@PreUpdate` and writes the result to the `stock_status` column, so the low-stock named query (`InventoryItem.findLowStock`) can filter with a plain comparison rather than recomputing status for every row on every read.

**Password hashing over plaintext or a fast general-purpose hash.** `PasswordHasher` uses PBKDF2WithHmacSHA256 with a per-user random 16-byte salt and a configurable iteration count (65,536), explicitly avoiding both plaintext storage and a fast hash (e.g. unsalted SHA-256) that would be practical to brute-force offline.

## Optimization Configurations

Hibernate's automatic schema generation creates the primary keys and foreign key constraints shown above, but it does **not** create secondary indexes on foreign key columns or on columns used in filtering (with the exception of `refresh_tokens`, whose indexes are declared on the entity). The following are recommended for the query patterns this application actually runs, and should be applied manually if not already present.

```sql
-- Speeds up vendor lookup by email during login/order-placement checks
CREATE INDEX idx_vendors_email ON vendors (email);

-- Speeds up SKU lookup, used on every stock update and order line check
CREATE INDEX idx_inventory_items_sku ON inventory_items (sku);

-- Speeds up InventoryItem.findLowStock, which filters on qty_on_hand vs reorder_threshold
CREATE INDEX idx_inventory_items_low_stock ON inventory_items (qty_on_hand, reorder_threshold);

-- PostgreSQL does not automatically index foreign key columns
-- these matter directly for order placement and order-history lookups
CREATE INDEX idx_orders_vendor_id ON orders (vendor_id);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);
CREATE INDEX idx_order_items_inventory_item_id ON order_items (inventory_item_id);

-- Speeds up username lookup during login and registration's uniqueness check
CREATE INDEX idx_users_username ON users (username);
```

`persistence.xml` also currently sets `hibernate.show_sql` to `true`, which is useful during development but adds logging overhead under load. This should be set to `false` before any production-style performance measurement, since Hibernate printing every statement to the console skews response-time results measured through JMeter or Postman.

## Applying the Schema

Because `hibernate.hbm2ddl.auto` is set to `update`, the tables above are created automatically the first time the EAR deploys against a fresh database (`java:/jdbc/Supply_ChainDS`). To apply the recommended indexes, connect with `psql` against the deployed database and run the statements above once, after the first successful deployment.
